## 4. 测试策略与方法

| 方法 | 应用示例 |
|---|---|
| **等价类划分** | 登录（正确 / 密码错误 / 缺参）；发布求助（正常 / 缺标题 / 缺必填） |
| **边界值分析** | 标题 20/21 字、描述 200、标签数量 3、昵称 20/21、年龄 0–150/200、信誉区间 |
| **场景法（主流程）** | 发布 → 接单 → 开始 → 完成 → 确认 → 评价 → 感谢信 → 故事卡 |
| **状态迁移法** | 订单状态机非法迁移断言（如已完成单再被接单→接单冲突、已取消单不可「再来一次」） |
| **异常/健壮性** | 无 token、错误 token、普通用户访问管理端、非法枚举值 |
| **权限/越权** | 仅「另一方」可确认结算；非参与人不能申诉；接单者专属照护提示 |
| **幂等/重复提交** | 重复确认结算、重复举报同一帖子、重复注册用户名 |
| **限流** | 发布/登录/聊天按分钟限流，超限返回 `30005` |
| **自动化断言** | 每条请求断言 HTTP 200 + `body.code` + 关键字段（类型/等值/数值范围）+ 响应时间阈值 |

> 说明：系统约定**业务错误也返回 HTTP 200**，因此断言的核心是响应体 `code`，而不是 HTTP 状态码——这是本项目测试设计中最关键的一点。

## 6. 典型用例设计（节选）

- **登录鉴权**：正常登录校验 `data.token` 为字符串、昵称一致；密码错误断言 `code=20001`；缺参断言 `code=10001`；登录后自动保存 token 供后续请求使用。
- **发布校验（等价类+边界值）**：缺标题 `10001`；标题 21 字 `10002`（CONTENT_TOO_LONG）；非法标签 `10001`；远程类型却传 `addressId` `10001`；上门类型缺地址 `10001`；同用户待响应订单达上限 `30003`。
- **主流程状态机**：接单→开始→完成→确认结算，逐节点断言 `status` 流转（PENDING → ACCEPTED → IN_SERVICE → PENDING_CONFIRM → COMPLETED）；完成后重复确认 `40003`；已完成单再被接单 `40001`。
- **释放/取消/再来一次**：接单者放弃后订单回到 PENDING；求助者取消后为 CANCELLED；已取消订单「再来一次」被拒 `40002`（仅 EXPIRED 本人可重发）。
- **社区审核**：正常发帖进入审核后发布；正文命中 BLOCK 级敏感词（如「刷单」）时置 `PENDING_MANUAL` 转人工审核，管理员审核通过后发布。
- **管理端**：概览、用户/订单/申诉/帖子查询与操作（封禁/解封/信誉调整/审核/隐藏/删除/回复反馈）。

## 7. 测试过程中发现并校准的问题

首轮执行 520 条断言出现 9 条失败，逐条定位后全部修复/校准（非产品缺陷，多为用例设计或环境配置问题）：

| # | 现象 | 根因 | 处理 |
|---|---|---|---|
| 1 | 注册新用户返回 `10001` | 自动生成用户名超 20 位且不符合 `^[a-zA-Z0-9_]{4,20}$` | 改为合法且唯一的用户名 |
| 2 | 隐私协议同意返回 `10001` | 版本号传 `1.0`，服务端要求等于配置 `privacy.policy_version='v1.0'` | 改为 `v1.0` |
| 3 | 待响应达上限未触发 `30003` | 测试期把 `order.pending_limit` 调成 10 | 初始化显式设为 2，并选已有 2 条待响应的账号 |
| 4 | 已完成单再被接单实际返回 `40001` | 状态机返回「接单冲突」而非「状态不允许」 | 断言校准为 `40001` |
| 5 | 已取消单「再来一次」返回 `40002` | 重发仅限 EXPIRED 本人 | 改为反向用例，断言 `40002` |
| 6 | 提交申诉断言失败 | 返回 `data` 为对象 `{id}`，非数字 | 断言 `data.id`、保存 `data.id` |
| 7 | 管理员审核新帖 `40002` | 普通新帖默认自动发布，无待审态 | 正文植入 BLOCK 敏感词触发 `PENDING_MANUAL` 后再审核 |
| 8 | 重复举报同一帖子 `40003` | 同一用户对同一帖子只能举报一次（跨轮次重复） | 改为举报本轮新建的帖子，保证可重复执行 |
| 9 | 批量重跑大量 `20001` | 上一轮收尾把登录限流恢复为 5/分钟，重跑时登录被限流（`30005`）导致 token 为空 | 初始化改为「先调高限流再登录」，消除顺序缺陷 |

另修正一处执行顺序依赖：初始化脚本把「调整限流/上限」放在登录之前，保证连续重跑稳定。

## 8. 结论与建议

- 核心业务链路的接口功能、状态流转、参数校验、鉴权与限流均按预期工作，回归通过率 100%。
- 测试集合已参数化（环境变量、动态 token、动态 ID），可在重置数据后一键重跑，适合作为持续回归资产。
- 建议后续：接入 CI（GitHub Actions 起服务 + newman 执行）、补充并发/性能场景（可迁移 JMeter）、对敏感词与审核策略做更细的分类用例。

## 附录 A · 业务码约定

`0` 成功；`10001` 参数校验失败；`10002` 内容过长；`10003` 内容违规；`20001` 未登录/凭证无效；`20002` 登录过期；`20003` 无权限；`30003` 待响应达上限；`30005` 触发限流；`40001` 接单冲突；`40002` 状态不允许；`40003` 重复提交；`50001` 系统错误。
